# Manotes tasks

- Purpose: Manage development work in the `manotes` graph.
- Recordbook: The main checkout's `.tasks` directory, shared by all workspaces. Prefix `manotes` commands with `tasks --` to run them there.
- Read [manotes-cli](../manotes-cli/SKILL.md) for querying, creating, editing, and syncing records.
- Graph rules: Read `.tasks/AGENTS.md` with `tasks AGENTS`.

## Read tasks

Run from the repository or a nested workspace, in the Nix devshell:

```sh
# Active tasks, grouped by state and sorted by priority.
tasks

# Complete task body.
tasks task:ABCD
```

```sh
tasks -- manotes execute <<'JS'
// CLI project tasks. Use "task:ABCD" as the target to find dependent tasks.
const records = await api.list({
  filter: [{ _tag: "cmp", val: [["link", "->", "project:cli"], "exists", true] }],
});
const tasks = records.filter(record => record.title?.startsWith("task:"));
await api.showList("oneline", tasks);
JS
```

## Start work

- Before working on a task, append `Session: <id>, cwd: <absolute path>` to its body via `tasks -- manotes execute` and `api.editRecord`. Use `pwd` in the working checkout, not the task recordbook.
- Get your OMP PID with `ps -o pid,ppid,comm -p $$`, following PPIDs if needed. Run `lsof -p <omp-pid> -Fn`, read the open `sessions/...jsonl` file's `type: "session"` header, and use its `id`.

## Complete tasks

- Keep tasks in `state:in-progress` while awaiting user review, even after implementation and verification pass.
- Mark a task `state:done` only after the user has reviewed and approved the result and explicitly says the task is done. Approval to implement or run checks is not approval to mark it done.

## Create and update tasks

Use `tasks -- manotes execute` for scripts.

- Generate a four-letter code, then prefix it with `task:`:

```sh
pnpx --silent nanoid@5.1.5 --size 4 --alphabet ABCDEFGHIJKLMNOPQRSTUVWXYZ
```

- Use `task:ABCD` as the actual record ID when calling `api.createRecord`, producing `task:ABCD.md`. Do not request an autogenerated record ID.
- Regenerate the code if that ID already exists. Keep the ID when renaming the task.
- Keep one task per record, with a short description and observable completion criteria.
- Put exactly one project, one state, and one priority backlink in the first paragraph after the heading. The board reads assignments there.

| Assignment | Record IDs                                                           |
| ---------- | ------------------------------------------------------------------ |
| Project    | `project:web`, `project:cli`                                       |
| State      | `state:backlog`, `state:todo`, `state:in-progress`, `state:done`   |
| Priority   | `priority:urgent`, `priority:high`, `priority:mid`, `priority:low` |

Task body:

```markdown
# task:ABCD Short description

[project:cli](./project:cli.md) [state:todo](./state:todo.md) [priority:mid](./priority:mid.md)

Describe the work.

## Done when

- State the observable completion condition.
```

- Change an assignment by replacing its existing backlink, not adding a second one.
- Link dependencies to the prerequisite task, for example `Depends on [task:WXYZ](./task:WXYZ.md).`
