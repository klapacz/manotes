## Summary

Added a public waitlist flow that lets unauthenticated users submit an email, checks whether the account is already active, and otherwise records a waitlist account.

## The Why

Sync is intentionally gated behind authenticated, manually activated accounts. Before this change, unauthenticated users only saw sign-in affordances, which made the hidden activation requirement confusing and gave new users no clear next step.

The waitlist flow makes that state explicit without weakening the session model: waitlisted users do not get sessions, do not touch Cloudflare Access identity resolution, and cannot access sync until they are manually activated.

## Design Decisions

The accounts Durable Object now tracks account `status` as `WAITLIST` or `ACTIVE`. Existing session creation uses the same account store but only succeeds for `ACTIVE` accounts, preserving the manual activation model. Public waitlist signup uses a separate `checkWaitlist` path that finds an existing account or creates a new `WAITLIST` account.

The public endpoint is modeled in the shared session API as `POST /api/waitlist`, but it deliberately has no session middleware. It accepts an email payload, returns only `{ status }`, and treats Durable Object RPC failures as infrastructure defects rather than user-actionable typed errors.

Email validation lives in a shared schema module so the worker API and web form use the same normalization and validation rules. The current validator is intentionally simple and can be tightened later without changing the route shape.

On the web, the home screen now offers a “sign in or join the waitlist” dialog for signed-out users. `ACTIVE` responses redirect to login, while `WAITLIST` responses show an inline confirmation. This keeps sync capability gated by the existing session atom while giving unauthenticated users a clear path forward.

Operationally, activation remains a two-step manual process: add the email to the Cloudflare Access policy and flip the account status to `ACTIVE` in the accounts database. Rate limiting and admin tooling are left as follow-up work.
